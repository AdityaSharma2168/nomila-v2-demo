1 · Canonical storage model

Seven logical entities from §28.3. Six are new tables; the seventh, durable content, reuses media_assets (section 8). All are athlete-scoped, additive, and written only behind the flag. The contract (sanitizer v1)

  1. Exact-value redaction first. The sanitizer receives the set of live secrets for the call (the connection's access and refresh tokens, the discovery token, the YouTube API key) and replaces any string containing one of them with <redacted:secret>, everywhere in the tree. This catches a token wherever it lands, including inside a URL or an error message.
  2. Key-name redaction. Any object key matching /^(access_token|refresh_token|id_token|client_secret|authorization|api_key|apikey|key|secret|password|signature|sig)$/i has its value replaced, at any depth.
  3. URL handling. Any string that parses as a URL has its query string removed when it contains a parameter matching rule 2 or the provider's known signing parameters (x-expires, x-signature, refresh_token, _nc_*, oh, oe); the path is kept so the payload still says which media it was. Paging URLs are dropped entirely and replaced with the bare cursor.
  4. Request records store path and an allow-list of parameters (fields, metric, metric_type, period, breakdown, limit, since, cursor, pageToken, part, ids, dimensions, startDate, endDate). Nothing else.
  5. Assert before insert. The ingest function re-runs a detector over the final JSON text (/access_token|refresh_token|Bearer\s|client_secret|key=AIza/ plus every live secret value) and refuses the insert if anything matches. A refused insert fails the sync run with status failed and reason sanitizer_leak; it never degrades to storing.
  6. Versioned. sanitizer_version is written on every payload row; a rule change bumps it.

Tests

  • Fixture per location above, built from redacted real responses, asserting the exact output and that the injected fake token strings are absent from the serialized result.
  • A property test: for random nesting depth and key placement, no injected secret survives.
  • A leak-detector test that the assertion in rule 5 refuses a payload with a token in a paging URL, a header echo and a nested error.
  • A boundary test that no adapter module imports connectedAccounts's row type into an envelope.
  • A scheduled audit query (the one used for this finding) as a script, runnable in CI against a scratch database and by hand against dev.

Remediation of existing rows (decision D7). The 82 raw_metrics rows are display-layer data. Proposal: a one-off, marker-guarded script that rewrites raw_metrics in place through the same sanitizer, and rotates the affected Instagram token by forcing a refresh. The display projection does not read paging URLs or cover query strings, so nothing the athlete sees changes.

Windows (decision D6). Proposal: compute every distribution feature for 30 and 90 days, growth for 30 and 90, cadence for 30 and 90, with 7-day variants only for cadence and follower growth. as_of defaults to the latest observation; the Mia command takes it as an argument.

6 · Source precedence at the metric and window level

  1. For each (identity, entity, metric_key, window) the resolver collects every observation whose observed_at falls in the window, grouped by source_class.
  2. Authority: connected_verified > platform_public > web_researched > imputed. The highest class with at least one fresh observation (freshness per metric from the research_freshness family, social_public 7 days, social_connected 2 days) wins the window; lower-class observations are ignored for calculation but stay in the table.
  3. Freshness does not fall through silently: a stale connected observation with a fresh public one yields the public value and a lower source_class on the feature, and the resolution is recorded in inputs.
  4. inferred never competes with observations. It is only ever a feature (non_follower_reach_share, content_format when the provider does not state it) and its row carries the evidence ids it was derived from.
  5. Unknown stays unknown: if no observation of any class exists in the window, the feature row is not written. There is no zero. Step 4's priors fill the gap and set imputed.
  6. Superseded observations are never deleted or flagged; supersession is a read-time decision that depends on the window and the freshness parameters, so it must be recomputable.

This is the same rule refreshScores.pickBestPerPlatform applies today at the level of a whole platform row (connected 4 > provider 3 > discovery 2 > research 1, 45-day freshness), moved to the metric level and made explicit in lineage. The Mia validation compares the two.

9 · The Mia validation fixture

One command, deterministic, no network:

npx tsx --require dotenv/config server/scripts/socialFeatureVector.ts --athlete dc8f37f1-… --as-of 2026-09-09T00:00:00Z --out ./out/mia-2026-09-09.json
# or, without a database, from committed redacted fixtures:
npx tsx server/scripts/socialFeatureVector.ts --fixtures server/services/intelligence/social/__fixtures__/mia --as-of 2026-09-09T00:00:00Z

Output is one JSON document with three sections and a lineage index: raw (the sanitized payloads used, by sync run and page, with hashes), observations (every row that fell inside any window, grouped by entity and metric, with source_class and observed_at), features (every feature row with value, n, window, source_class, confidence, calculation_version and the observation ids it used). A companion --explain followers_growth_30d prints the resolution for one feature: which observations were candidates, which class won, why the others were ignored. The jest suite runs the same calculator over the committed fixtures and asserts exact values for a hand-checked subset (medians, p75, cadence, growth), so a change in the calculator is a visible diff.

Where the fixture data comes from. Mia's 72 Instagram, 73 TikTok and 6 YouTube daily rows (30 Jun to 10 Sep) hold account facts, account insights, 18 to 20 recent media with counts per day, and demographics; her 569 media rows hold posted_at, formats, counts and enriched insights for 34 videos. The backfill (section 10) turns these into observations with source_method legacy_snapshot and legacy_media_assets; redacted copies of a few days plus one native envelope captured on the first flagged sync become the committed fixtures. Her YouTube connection is expired, which the command will report as coverage, not as zero (§29.1).

Dual write, behind a flag

  • SOCIAL_SUBSTRATE_WRITE (default off in both YAMLs). Off: the code path is the old one, byte for byte. On: collectSocialAnalytics, collectDiscoveryAnalytics, the backfill tick and enrichTopPostInsights run sanitize → store → adapt → features after their existing writes; a failure in the new path is logged on the sync run and never fails the old write.
  • No reader of the new tables in production; the score, the Growth tab and Mila are unaffected by construction.

Backfill

  1. backfillSocialIdentities.ts: from connected_accounts (active, expired and revoked, so history is preserved) and athletes.socials; marker-guarded, idempotent.
  2. backfillSocialObservations.ts: walks social_analytics_snapshots (218 rows) and media_assets (~750 social rows) into observations and distributions with source_method legacy_*, observed_at = snapshot_date or metadata timestamps, definition_version legacy/1. Sanitizes raw_metrics on the way (decision D7 decides whether it also rewrites the source rows). Idempotent on the unique constraints.
  3. socialFeatureVector.ts for Mia at three as_of dates as the acceptance check.

12 · Access model check (ADR-015, ADR-016)

Recorded after the design was written, against the two LOCKED decisions: a user is not an athlete, and affiliation does not imply access to private data. Nothing below changes Step 1 scope; it says where the proposal and the current code stand.

ItemStatusNote
Domain owner of every new tablecompliantsocial_identities, sync runs, payloads, observations, distributions and features are owned by athlete_id, never by an auth user. No organization_id anywhere.
Consent linkagecompliantConnected data is tied to the athlete's own connected_accounts row through social_identities.connected_account_id and source_method; that row is the consent record a future authorizer reads.
Private versus public separabilitycompliantsource_class on every observation, distribution and feature distinguishes connected_verified (private, consented) from platform_public and web_researched (public). A feature's class is the lowest authority of its inputs, so a number derived from private data is never public by default.
media_assets reuseflagThe table already mixes consented uploads (origin = upload, camera roll) with public-facing posts. Reuse does not worsen this, but origin becomes the access-relevant field for content and must be kept accurate; a Story row, if created, would be private content.
Current code: athletes doubles as the user tableflagathletes.auth_id, account_roles → athletes.id, and requireAuth setting req.athleteId all assume athlete = user. Step 1 does not touch this. Step 3 (identity confirmation) must link a user to an athlete rather than treating the signup row as the athlete; that is the first place ADR-015 changes a design.
Backfill of identities from connected_accountscompliantIdentity rows are keyed by the platform account id, not by who logged in; a second user later acting for the same athlete needs no change here.
