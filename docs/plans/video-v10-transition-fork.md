# Card 2's fork: a third `StitchTransition` kind, or an inserted clip?

**Written 2026-09-20, before card 2 is built. For Adi to ratify.**

Adi's stated lean is **(i)** — a third `StitchTransition` kind that materializes into a clip, as a
first-class transition — over **(ii)**, inserting an ordinary clip, on the grounds that (i) is cleaner
authoring and (ii) is second-class. **Recommendation below is (ii), plus provenance**, on a fact the
lean did not have in view.

## ⚠️ The stitch queue is deliberately incapable of spending, and a test pins it

`stitchRunner.test.ts` — "no spend surface" — walks the import graph out of `stitchRunner.ts` and
asserts it reaches **none** of:

```
studio/generate.ts · studio/router.ts · studio/adapters/ · studio/preview.ts
studio/previewStore.ts · studio/interpret/ · studio/compile/ · studio/qa/ · lib/models.ts
```

It is not a lint. The same suite pins that stitching is ticked by **its own endpoint with its own lock
key**, explicitly so the free queue is never serialised behind the money path. And the walk is
conservative by design: it reads import specifiers out of the SOURCE and counts an `import type` as a
real edge, because a type import is one refactor from being a value import. `studio/types.ts` exists
in its current shape because of exactly that.

**A bridge costs money.** So option (i) in its natural form — the stitch pipeline notices a `bridge`
transition and generates the clip — is not "more work". It is blocked by an invariant somebody chose,
and making it work means either moving generation into the free queue (reds the guard, and serialises
stitching behind a paid provider call) or inventing a cross-queue dependency: a stitch spec that
cannot run until the video queue finishes a job, with its own pending state, its own failure path, and
its own spend approval ahead of a stitch the athlete already approved.

## What (ii) gets for free

A bridge generated by the ordinary video path is an ordinary `media_assets` VIDEO row, so it inherits:

- **spend** — `assertVideoEnabled`, `spendCaps`, the approved figure, the rolling day total;
- **the poster and the real duration** — `processPosterBatch` picks up any `origin IN ('upload','generated') AND media_type='VIDEO'` row and writes `gcs_thumb_path` and `duration_seconds_precise`;
- **QA** — the V9 verdict pipeline, unchanged;
- **the timeline** — it is a clip; reorder, trim, crossfade and the memory ceiling all already work.

`StitchTransition` stays `cut | crossfade`, the spec is untouched, and the no-spend guard stays green
without being argued with.

## The one thing (i) genuinely buys, and how to keep it

Provenance. Under (ii) a bridge is an anonymous clip that can be dragged somewhere it makes no sense,
and nothing records that it was built to join A to B.

**That is a field, not a `StitchTransition` kind.** A `role: "bridge"` plus the two asset ids it was
generated between gives the timeline everything it needs to label it, keep it adjacent, and refuse a
reorder that orphans it — without the bridge's generation ever entering the stitch graph.

**The first-classness Adi wants is a UI property, not a spec property.** "Add a transition between
these two clips" can be one control on the join TimelineBuilder already renders (it toggles
scissors ↔ shuffle per join today); that it produces a clip underneath is an implementation detail she
never sees.

## Recommendation

**(ii) plus a `bridge` provenance field.** It keeps the money on the money path, leaves a deliberate
invariant intact, inherits poster/duration/QA/timeline for nothing, and gives up only a spec shape
whose user-visible benefit a field and a UI control already deliver.

**If Adi still wants (i)**, the honest cost is a cross-queue dependency and a re-argued no-spend guard,
and that should be its own card with its own plan — not a line item inside card 2.
