# Studio Content Engine — Wave 1 inventory audit

> Audited 2026-08-27 against `adi/studio-inventory-audit` (branched off `adi/voice-search-identity`).
> Every claim below was read out of the actual source or queried read-only against the live DB
> (SELECT only — no writes, no DDL). Line refs are `file:line` at that commit.
>
> **PII note:** athletes appear as truncated UUIDs. Names were reported to Adi out-of-band and are
> deliberately not committed. Brand names are companies, not people, so they are named.

---

## TL;DR — what changes the Wave-1 design

1. **The Studio tab already exists and ships.** `client/screens/StudioScreen.tsx` is a complete
   creator workspace (Pitches shelf, status pills, media library, create flow) wired into a real
   `StudioStack`. Task 3 is **not** "build the tab" — it's "replace the fake `SAMPLE_POSTS` strip
   (`StudioScreen.tsx:180`) with a real, flagged campaign-workspace route."
2. **The generation spike is single-athlete constrained.** Exactly **one** athlete in the whole
   database has enriched, usable media (274 stored top-level assets, all vision-tagged and embedded).
   The only other athlete with any `media_assets` rows has 8, all `status='failed'`. The "top 5
   athlete/brand pairs" is therefore one athlete × five brands. See §10.
3. **All three reserved tables are empty** — `content_brands`, `content_posts`, `kit_content` = 0 rows.
   They are schema-only. We define their semantics; nothing to migrate around.
4. **There is no `getAthleteContext()`.** The brand side has a clean, reusable
   `getBrandContext(brandId)`; the athlete side is ~120 lines inlined in the deck builder. The
   router/scaffold should assume we extract it (§6).
5. **The media pool is smaller than the raw count suggests.** Of 274 tagged assets, the VLM marked
   **196 `disposition='reject'`**; only ~60 are `as_is`. Generation should treat `reject` as
   *"regenerate/replace this"*, not *"discard"* — that's the actual product opportunity.

## 1 · Media

### `server/lib/mediaStore.ts` (96 lines) — GCS wrapper
Thin, ADC-authed wrapper on bucket `MEDIA_BUCKET` (default `nomila-v2-athlete-media`). No DB access.

| Export | Signature | Notes |
|---|---|---|
| `rehostFromUrl` | `(url, basePath, maxBytes?) => Promise<RehostResult \| {skipped:"size"} \| null>` | Buffers whole file in memory; ext derived from response `Content-Type`, never the URL |
| `signedUrl` | `(gcsPath, ttlMs = 3_600_000) => Promise<string>` | v2 signing (no `version` arg) |
| `uploadLocalFile` | `(localPath, gcsPath, contentType) => Promise<void>` | The one we need for writing generated bytes |
| `signedUploadUrl` | `(gcsPath, contentType, ttlMs = 15min) => Promise<string>` | v4 signing; client must PUT with *exactly* `contentType` |
| `uploadKind` / `uploadObjectPath` / `UPLOAD_LIMITS` | — | image ≤25 MB, video ≤200 MB |

**Reusability: high, with one gap.** `uploadLocalFile` covers "write a generated asset to GCS", but
there is **no buffer-upload helper** — a provider returning bytes in memory forces a `/tmp` round-trip.
`rehostFromUrl` almost fits a provider returning a URL, except it hardcodes the 25 MB `MEDIA_BUCKET`
default cap and its EXT map has no `image/gif` / `video/webm`.

**Gotchas**
- `uploadObjectPath()` hardcodes `athletes/<id>/uploads/<uuid>.<ext>`. Generated assets need their own
  prefix (`athletes/<id>/generated/…`) or they become indistinguishable from athlete uploads, and
  `routes/media.ts:216` will happily accept them as `origin='upload'`.
- `signedUrl` is v2, `signedUploadUrl` is v4. Inconsistent but both work; don't "fix" it in Wave 1.

### `server/routes/media.ts` (241 lines) — the library read/write API
Mounted under `/api/v1/me`. Three routes, all `requireAuth` + `req.athleteId!`-scoped:
`GET /media` (keyset paginated by `(posted_at DESC, id DESC)`, `PAGE=24`), `GET /media/:assetId`
(full vision analysis), `POST /media/upload-url`, `POST /media`.

`shapeItems()` (`:32`) is the canonical asset→client shape and is worth reusing verbatim: it signs
URLs fresh per request, nests carousel children, and surfaces `enriched`, `brand_safe`, `shot_type`,
`brands_visible`.

**Gotchas**
- **`GET /media` never filters `deleted_at`.** Soft-deleted assets will appear in the library the
  moment anything writes that column. Today it's 0 rows everywhere, so it's latent, not broken.
- `origin` is already a documented filter value set: `connected|upload|generated|discovery`
  (`:78`) — `generated` is anticipated but nothing writes it yet.
- `POST /media` (`:216`) enforces the `athletes/<id>/uploads/` prefix. A generated-asset register
  route must **not** reuse this handler; write a sibling that enforces the generated prefix.
- The first page fires two extra aggregate queries (summary + top-10) with no index behind the
  `ORDER BY coalesce((insights->>'video_views')::bigint, …)` — fine at 564 rows, not at 100k.

### `server/services/videoPoster.ts` (175 lines) — the ffmpeg worker
`processOneVideo(row)` → `"postered" | "transcoded" | "failed"`; `processPosterBatch(limit=3)` →
`{processed, failed, transcoded, remaining}`. Poster is mandatory (frame at 1s, falling back to frame
0), transcode to 1080p H.264 faststart is best-effort. ffmpeg reads **straight from a signed GCS URL**
(streams; never buffers input) and writes only small outputs to `/tmp`.

**Reusability: high — this is the template for every async generation worker.** It has all four
properties we need: a row-driven work queue, a per-run wall-clock budget (`RUN_BUDGET_MS = 220_000`,
under Cloud Run's 300s), a poison-pill guard (`metadata.poster_error` removes a row from the queue
forever), and a `remaining` count so the cron knows whether to tick again.

**Gotchas**
- Requires the `ffmpeg` binary in the image — **confirmed present** (`Dockerfile:27–30`, apt-installed
  for exactly this worker), so a generated-video post-process can use it.
- The poison-pill pattern writes the error into `metadata` — if we reuse `metadata` for generation
  provenance we must not clobber it. Note `:87` does `{...(row.metadata ?? {}), poster_error}` — a
  read-modify-write with **no optimistic concurrency**. Two workers on one row lose an update.

### `server/skills/mediaBackfill.ts` (131 lines) — resumable ingestion
`backfillAthletePlatform(athleteId, platform, budget=300)` / `backfillAthlete` / `backfillAllAthletes`.
Checkpoint lives in `media_backfill_state (athlete_id, platform)` PK with `cursor`, `status`
(`pending|running|complete|error`), `items_seen`, `last_error`.

**This is the reference implementation for a resumable chunked job** and the pattern the generation
job table should copy: pace, don't truncate; `BACKSTOP = 10_000` is explicitly a broken-loop guard,
not a content cap; failures park the row at `error` and never throw.

**Gotcha:** `saveState` uses `onConflictDoUpdate` on the composite PK, but nothing prevents two
concurrent ticks for the same (athlete, platform) — there's no lease/lock. At one cron caller it's
fine; a user-triggered "generate now" **plus** a cron would race.

## 2 · Understanding & search

### `server/lib/visionTag.ts` (60 lines)
`tagAsset(gcsPath) => Promise<AssetTags | null>` — Gemini Flash on Vertex, image inlined as base64,
`responseMimeType: "application/json"`, temp 0.2. Returns 13 fields; the ones generation cares about:
`athlete_present`, `athlete_prominence`, `shot_type`, `description`, `brands_visible[]`,
`aesthetic_quality`, `brand_safe`, `setting`, `attire`, `vibe`, `hero_suitability`, **`disposition`**
(`as_is|crop|enhance|reject`), `edit_note`.

`heroScore(t) => number` (`:56`) is the rankable blend:
`0.45·hero_suitability + 0.30·aesthetic_quality + 0.25·athlete_prominence`, hard-zeroed when
`!athlete_present || !brand_safe`, and `0.05` for `text_graphic`.

**This is the single most valuable thing in the audit for generation.** `disposition` + `edit_note`
are already an *edit instruction* the VLM wrote per asset — "crop: subject off-center", "enhance:
worth upscaling/relighting". Nothing reads them today (grep: only `visionTag.ts` itself). They map
directly onto `image.edit` tasks.

**Gotchas**
- The prompt is hardcoded to *"an elite young female athlete's PREMIUM brand media kit"* (`:29`).
  Gendered and kit-specific. Reusing `tagAsset` for generated-asset QA will inherit that framing.
- Swallows every error to `null` — no retry, no reason. A quota failure is indistinguishable from a
  malformed image.
- Images only. There is **no video tagging path** — `mediaEnrichment` tags a video's *poster frame*.

### `server/services/mediaEnrichment.ts` (81 lines)
`enrichAthleteMedia(athleteId, {limit?, reEmbed?})` and `enrichNextChunk({athleteId?, chunk=20})`
→ `EnrichResult & {remaining}`. Idempotent per asset (skips when both `metadata.vision` and
`metadata.embedding` exist), bounded concurrency `CONC=4`, resumable via the `UNENRICHED` predicate.

**Gotchas**
- Same **read-modify-write on `metadata`** as videoPoster (`:39,43`) — `{...meta}` then a full column
  overwrite. Vision and embedding writes inside one asset are serialized, but a concurrent poster
  write is not.
- `enrichRows` counts a null tag *and* a null embedding as two separate `failed`, so `failed` can
  exceed `total`.

### `server/services/mediaSearch.ts` (121 lines) — **the casting API**
```ts
searchMedia(athleteId, {
  brief?, filters?: {brandSafe, shotTypes, excludeBrands, athletePresent, playableVideo},
  purpose?: "hero"|"fit"|"proof"|"video"|"generic",
  recencyHalfLifeMonths?, k?, diverse?, diversityThreshold?
}) => Promise<SearchResult[]>
```
Scores = purpose-weighted blend of `heroScore` × normalized embedding similarity × recency × views,
then greedy diversity dedup by embedding cosine (`> 0.92` = near-duplicate).

**Reusability: very high — this is exactly the reference-image picker for `image.edit`.**
`filters.excludeBrands` is already the conflict filter; `diverse: true` already kills camera-roll bursts.

**Gotchas — both matter at scale**
- **It loads every one of the athlete's assets into Node on every call** (`:47`, no `LIMIT`), including
  the full 1408-float embedding per row, then filters/scores in JS. At 274 assets ≈ 385k floats per
  call. Curation fires ~6 `searchMedia` calls per deck build. This is the first thing that breaks.
- Similarity is **min-max normalized across the candidate set**, so `sim` is relative to the current
  result set, not absolute. Two calls with different filters produce non-comparable scores. Don't
  threshold on it.
- Filters are *permissive on missing tags*: `if (f.brandSafe && x.tags && !x.tags.brand_safe)` — an
  untagged asset passes every filter. Generation must gate on `tags != null` explicitly.

### `server/lib/mediaEmbed.ts` (67 lines)
`embedText(text)` / `embedImageGcs(gcsPath)` → `number[] | null` (1408-d, Vertex
`multimodalembedding@001`, one shared image+text space), plus `cosine(a,b)`. Hand-rolled OAuth token
cache with a 5-min refresh margin. Best-effort → `null`.

**Gotcha:** `embedText` truncates to 1024 chars silently. A long generation brief loses its tail.

## 3 · Intelligence

### `server/skills/researchBrand.ts` (157 lines)
`researchBrand(brandId, brandName, domain, {force?}) => Promise<void>` — 4 parallel Gemini
Google-Search-grounded queries → Kimi extraction → `UPDATE inbox_brands`. 90-day re-enrichment guard
unless `force`. Writes `category`, `description`, `brand_tier`, `audience_summary`,
`sport_categories`, `known_athlete_partnerships`, `enriched_at`, and the full `enrichment` jsonb
(`content_style`, `recent_campaigns`, `competitors`, `brand_values`, `product_categories`,
`partnership_style`, `markets`).

**Reusability: high, read-side.** For generation we want the cached record, not a re-run —
`getBrandContext()` below is the right door.

### `server/services/shotList.ts` (184 lines) — the Strategist
Three exports, and the split between them is the pattern to copy:

| Export | Signature | Role |
|---|---|---|
| `getBrandContext` | `(brandId) => Promise<BrandContext \| null>` | **Pure read** of `inbox_brands` → a typed 12-field context. No model call. |
| `deriveShotList` | `(athleteId, brand?) => Promise<ShotList \| null>` | Gemini Pro → `{facets[], shots: ImageBrief[]}`. `ImageBrief = {card, role, facet, mood, beat, searchQuery}`. |
| `deriveDeckPlan` | `(athleteId, brand, signals: DeckSignals) => Promise<DeckPlan>` | Owns **composition** — card order, per-card image role, `galleryTarget`. |

`ImageBrief` is very close to what a generation task needs: `{role, facet, mood, beat, searchQuery}`
is a prompt skeleton with a retrieval query attached. A `GenerationTask` brief should extend this
shape rather than invent a parallel one.

**Gotchas**
- `deriveShotList` reads the athlete's context itself (`:135–147`) — a *second*, narrower copy of the
  same joins `mediaKitService` does. Two places already read athlete facts differently.
- `deriveDeckPlan` calls `deriveShotList` internally, so you cannot get the plan without paying for
  the Gemini Pro call.
- `MODEL = process.env.SHOTLIST_MODEL ?? GEMINI.pro` — good precedent: **model id from config, never
  at the call site.** Task 2's router must match this.

## 5 · The two rich athlete sources that go unread

Both are populated, both are athlete-side, both are invisible to the entire deck/generation path.

### (1) `athletes` first-party self-description — the athlete's own voice
`brand_voice`, `goal_archetype`, `secondary_goals`, `deal_preferences`.

Written by Mila's profile extraction (`server/mila/profileExtraction.ts:39–160`,
`server/mila/profileFields.ts`). Read by the **voice** path (`server/voice/athleteProfile.ts:222–240`,
`server/voice/profileRoute.ts:82–84`) and by `dealDetector`/`askTerms` for the rate floor. **Never read
by `mediaKitService`, `shotList`, `narrator`, `curator`, or `mediaSearch`.**

Live fill across 25 athletes: `brand_voice` 1 · `goal_archetype` 9 · `secondary_goals` 10 ·
`deal_preferences` 4 · `media_rights_ack_at` 1.

**Why it matters most:** `brand_voice` is stored as `{tone, phrases, avoid}`. That is *literally a
prompt-tone spec, already structured*, and the Narrator instead runs a hardcoded persona — *"You are
an elite brand copywriter"* (`narrator.ts:145`). For generated captions and image prompts this is the
single highest-value unread field in the schema. Low fill today, but it's a fill problem, not a
plumbing problem.

### (2) `athlete_snapshots.research` — everything except two keys
The deck reads `research.achievements` and `research.brand_mentions`. The grounded 5-query research
pipeline also writes, and nothing in production ever opens:

| Ignored key | Live counts (per athlete, latest snapshot) |
|---|---|
| `press_mentions` `[{outlet, headline, date}]` | 25 · 23 · 15 · 10 · 7 · **5** · 0 |
| `media_assets.images` `[{url, source, description, type}]` | 4 · 1 · 0 … |
| `media_assets.videos` `[{url, source, title, platform}]` | 3 · 2 · 0 … |
| `nil_valuation_mentions` | 5 · 1 · 0 … |

| `profile` `{hometown, class_year, position, conference, division}` | present for all 7 |

The only code that touches them is `server/scripts/_inspectSnap.ts` (a debug script) and
`server/scripts/compareSearch.ts`. `press_mentions` in particular is per-athlete editorial context
— outlets and headlines — that a campaign concept should be grounded in.

**Honorable mention (partially read, so not counted):**
`social_analytics_snapshots.raw_metrics`. The deck opens only `demographics.country` and
`.gender`. For the one enriched athlete there are 58 IG + 59 TikTok snapshots carrying
`recent_media`, and 6 YouTube snapshots carrying the full `youtube` analytics block (retention %,

## 6 · The deck pattern (read-only — not modified)

### The chain
```
buildAndCacheKit(athleteId, {brandId, onStep})          kitCache.ts:86
  └─ assembleMediaKit(athleteId, {brandId, onStep})     mediaKitService.ts:119
       ├─ [inline athlete brief]                        :124–214   ← §4
       ├─ getBrandContext(brandId)                      shotList.ts:30   (pure read)
       ├─ deriveDeckPlan(athleteId, brand, signals)     shotList.ts:170  ← STRATEGIST (Gemini Pro)
       │    └─ deriveShotList → {facets[], shots[]}
       └─ Promise.all([                                 :275
            curateAthleteMedia(athleteId, {shotList, galleryTarget})   ← CURATOR
            narrateKit(narratorCtx, briefs)                            ← NARRATOR
            narrateWhyFits / narrateCampaignConcept / narrateActivationPlan
          ])
```

**Strategist → Curator → Narrator, with the shot list as the shared contract.** The shot list is
derived **once** and handed to both the Curator (image casting) and the Narrator (copy), so pictures
and words land the same facets. That single-derivation discipline is the thing to preserve.

### `curator.ts` (71 lines)
`curateAthleteMedia(athleteId, {recencyHalfLifeMonths?, shotList?, galleryTarget?})` →
`{hero, fit, audience, proof[], gallery[], video}`. Casts each featured slot by running that card's
`searchQuery` through `searchMedia`, tracking a `used: Set<sourceId>` so nothing repeats.
**Directly reusable** as the reference-image selector for generation.

### `narrator.ts` (479 lines) — the most transferable pattern in the codebase
Multi-model fan-out → gate → pool → judge:
1. `MODELS` (env `NARRATOR_MODELS`, default `gemini,kimi,fable`) all run **in parallel**, `OPTIONS`
   options per slot per model.
2. `applyGate()` (`:452`) — deterministic filter dropping any line that repeats a displayed fact,
   a proper noun, or a grade word. Model output is *filtered by code*, not trusted.
3. `poolOptions()` merges surviving options per slot.
4. `judgeOrder()` (`:243`) — an independent judge that **ranks only, never rewrites**; its pick
   becomes index 0 (the default), losers become the athlete's alternates.

**This is the shape the generation router should follow**: N providers in parallel → deterministic
gate → judge picks a default → the rest become alternates the athlete can swap to. It also means
"multiple candidates per slot" is already the established UX contract, not a new idea.

**Gotchas**
- Fable runs on the **Anthropic API** and returns `null` when `ANTHROPIC_API_KEY` is absent
  (`:34–38`) — silently degrades to 2 models.
- `narrateKit` returns `null` if *every* model fails; the assembler then falls back to templated copy.

### `kitRenderer.ts` (767 lines) + themes
`renderKitHtml(kit, theme?, opts?)` → a self-contained HTML card stack for public share links.
`listThemes()` enumerates `campaign` (baseline, inline) + `broadcast` / `immersive` / `luxe`
(`server/services/themes/*.ts`). Server-side only; the app renders the same `MediaKitData` natively.

## 7 · Streaming — the transport for the generation viewer

### `server/lib/sse.ts` (74 lines)
`openSSEStream(res, req) => SSEStream` with `status(msg)` / `token(t)` / `done(data)` /
`suggestions(list)` / `profileUpdates(list)` / `error(msg)` / `close()` / `abort()`, plus
`signal: AbortSignal` and `closed: boolean`. 15s keepalive (GFE drops idle connections); client
disconnect aborts the controller.

**Reuse it as-is.** To add generation events (`asset`, `cost`, `progress`), **extend the `SSEStream`
interface** — the codebase convention is never to write to `res` directly. Note the two existing
extra events (`suggestions`, `profileUpdates`) are *field-presence* events — `{suggestions:[…]}` with
no `done` field — so the client attaches them without a wire discriminator. Follow that.

### Server usage — `server/index.ts:779` and `:811`
```
GET /api/v1/athletes/:id/pitch-insights-stream?brandId=N
GET /api/v1/athletes/:id/pitches/:brandId/build-stream
```
Both `requireAuth`, both assert `req.athleteId !== req.params.id → 403`, both take an `onStep(label)`
callback into `sse.status(label)`, both `sse.close()` in `finally`.

**Gotcha:** neither passes `sse.signal` into the model calls — a client disconnect does **not** cancel
generation. For image/video generation that's real money. The generation stream must thread the
signal through `ProviderOpts`.

### Client — `client/hooks/use-build-stream.ts` (116 lines) + `BuildTimeline.tsx`
`pump()` reads the SSE body with `fetch` + a `ReadableStream` reader (EventSource can't send an auth
header). Steps are matched by **exact string equality** against a frozen list
(`BUILD_STEPS` / `RESEARCH_STEPS`), so a server-side label typo silently stalls the timeline.
`useStepStream` exposes `{run, cancel, running, activeStep, stepState, error}`; `BuildTimeline`
renders one row per step with a rail.

**Reusability: high, but the step list must become data.** Generation has a variable number of steps
(N assets), so a frozen `const` array won't do — the `done`/`status` contract should carry the step
list, or steps should be keyed by id rather than matched by prose.

## 8 · Cards, looks, and the edit overlay

### `client/components/card-native/`
15 card components (the `campaign` baseline) + three complete look directories (`luxe`, `broadcast`,
`immersive`), each with 13 ported cards, a `Chrome.tsx`, and a `theme.ts` token file
(e.g. `luxe/theme.ts` exports `LX` — noir/champagne/ivory/rouge + Bodoni Moda + Jost).

`looks.tsx` (160 lines) is the dispatch hub: `CardView` renders a card in the requested look and
**falls back to the campaign component for any type a look hasn't ported**, so a partial look degrades
gracefully. Adding a look = drop a directory + register it in `LOOKS`.

**Reusability for the campaign workspace: high.** The look system is the render target, and
`theme.ts` per look is exactly where generated-asset styling should read its palette from, so a
generated image matches the deck it will sit in.

### `server/services/cardOverrides.ts` (108 lines) — **the edit-survives-regeneration pattern**
```ts
CardOverrides = { order?, removed?, added?, copy?: Record<`${cardId}.${field}`, {text, pick?}>,
                  images?: Record<cardId, string | {path, poster?}>, theme? }
applyOverrides(kit, ov) => MediaKitData     // pure, applied at SERVE time
```
Keyed `(athlete_id, brand_id)` in `card_overrides`. The principle, stated at `:15`:
**the athlete edits a VIEW, not the source** — the base kit stays fully regenerable, and
`EDITABLE` (`:33`) whitelists exactly which crafted-copy fields may be overridden per card type.
The facts layer can never be overridden.

**This is the model for generation edits.** A regenerated asset must not blow away the athlete's
crop/caption/selection. Apply the same shape: overrides keyed by a stable id, applied at read time,
whitelisted fields only.

**Gotcha:** the override key is the **card id**, and image swaps key on `gcsPath`
(`routes/media.ts:53`). Generated assets need a stable identity that survives regeneration — a
`generation_id`, not the output path, or every regeneration orphans its edits.

## 9 · Jobs — how async workers are structured

**No queue, no Cloud Tasks.** The pattern is: Cloud Scheduler → `POST /api/internal/<name>-cron` with
an `x-cron-secret` header → a bounded, resumable batch executed **inside the request**.

- **Guard** — `cronSecretValid(req)` (`server/index.ts:107`), `crypto.timingSafeEqual` against
  `CRON_SECRET || INTERNAL_CRON_SECRET`. Returns 401 on mismatch.
- **Existing endpoints** — `archive-stale`, `media-poster`, `gmail-cron-sync`, `social-analytics`,
  `media-enrich`, `brand-refresh`, `score-refresh`, `re-enrich`, `discovery-collect`, `payments`.
- **The load-bearing lesson** — `media-enrich-cron` (`:576`) carries an explicit comment: the previous
  fire-and-forget version **never drained**, because *Cloud Run throttles CPU to ~zero after the
  response is sent*. It now `await`s inside the request under `BUDGET_MS = 160_000` with a `maxTicks`
  cap. **Generation jobs must do the same** — never `res.json()` then keep working.

**The four properties every worker here has**, and that the generation job must copy:
1. **Resumable** — a predicate finds unfinished work (`UNENRICHED`, `gcs_thumb_path IS NULL`).
2. **Idempotent** — already-done rows are skipped, so re-running is free.
3. **Chunked + budgeted** — bounded batch, wall-clock budget under the Cloud Run timeout, `remaining`
   returned so the caller knows to tick again.
4. **Poison-pill guarded** — a permanently-failing row is marked (`metadata.poster_error`,
   `media_backfill_state.status='error'`) and drops out of the queue.

**Gotcha:** none of these take a lease. Every worker assumes a single caller. Generation will have
*two* callers (a cron drain and a user pressing "Generate"), so it needs either a claim (`UPDATE …
SET status='running' WHERE status='queued' RETURNING`) or an advisory lock. **This is new machinery
Wave 1 has to add** — there is nothing to copy.

## 12 · Open questions for Wave 1 design

1. **Extract `getAthleteContext()`?** §4/§6 argue yes, but it touches `mediaKitService` — which the
   lane rules put off-limits. Options: a new read-only module that the deck builder *later* adopts,
   or leave the duplication and accept a third reader. **Needs a call.**
2. **`derived_from_asset_id` has no index or FK.** Generation lineage is unqueryable in reverse.
   Adding either is a schema change — out of our lane, needs Mia.
3. **Job leasing.** §9 — nothing in the codebase leases a row. Two callers (cron + user) will race.
   Wave 1 has to build this from scratch.
4. **`searchMedia` loads every asset per call** (§2). Fine at 274, not at scale. Do we bound it in
   Wave 1 or accept it for the spike?
5. **`sse.signal` is not threaded into model calls** (§7). For paid image/video generation a client
   disconnect should cancel. The router's `ProviderOpts` should carry an `AbortSignal` from day one.
