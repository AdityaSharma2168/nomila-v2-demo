2 · Schema

model_params: the versioned parameter store

Generalises the one-active-row pattern of scoring_weights to every parameter family the spec names: weights and sub-weights, lookup tables, priors, calibration functions, freshness TTLs, source policies, rate benchmarks. One table, one status machine, one activation rule, so every engine versions the same way (§15). scoring_weights is left exactly as it is; the marketability engine in Step 4 reads model_params and the two coexist until v7 is retired.

CREATE TABLE IF NOT EXISTS model_params (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family        text NOT NULL,          -- 'marketability' | 'signals' | 'priors' | 'cohorts' | 'research_freshness'
                                        -- | 'commercial_proof' | 'rates' | 'opportunity' | 'earnings'  (CHECK-free on purpose; closed in code)
  version       text NOT NULL,          -- 'v1.0-beta.1', 'v0.1-alpha' — never edited in place
  status        text NOT NULL DEFAULT 'draft',
  config        jsonb NOT NULL,
  hash          text NOT NULL,          -- first 12 of sha1(canonical JSON), for eyeballing against traces
  note          text,                   -- why this version exists
  created_by    text,
  created_at    timestamptz NOT NULL DEFAULT now(),
  activated_at  timestamptz,
  CONSTRAINT model_params_status_check CHECK (status IN ('draft','active','inactive','archived')),
  CONSTRAINT model_params_family_version_uq UNIQUE (family, version)
);
-- one live version per family, enforced by the database (same device as scoring_weights and prompts)
CREATE UNIQUE INDEX IF NOT EXISTS model_params_one_active_uq ON model_params (family) WHERE status = 'active';
CREATE INDEX IF NOT EXISTS model_params_family_idx ON model_params (family, created_at);

Why no CHECK on family: the same reason LOCKED_PROMPTS lives in code (0033's header). A family list a migration has to know about is one more place to keep in step with deploy DDL; the closed list lives in types.ts as ParamFamily. Why status and not a boolean: draft is the review state you asked for (never read), inactive is a superseded version kept for reruns (§15 "rerun historical profiles"), archived is retired.

athlete_snapshots: two nullable columns

ALTER TABLE athlete_snapshots ADD COLUMN IF NOT EXISTS as_of          timestamptz;  -- the instant the evidence set is "current at" (§21.1)
ALTER TABLE athlete_snapshots ADD COLUMN IF NOT EXISTS engine_version text;         -- the model_params version(s) that produced `score`, e.g. 'marketability=v1.0-beta.1'

Both null for every existing row and for every row the current writers insert; the score audit's history reader (scoreHistoryRoute) ignores unknown columns. Semantics for later steps: as_of defaults to created_at when a reader finds it null, so legacy rows need no backfill; engine_version null means "v7 scoring_weights active row at that time". Not added: a separate features snapshot table. That is Step 1's social_features plus a Step 4 feature-vector snapshot; adding an empty table now would be architecture on paper.

commercial_proof · v0.1-alpha (proposal, decision 4)

RuleProposal
Allowed sources for verified_commercial_value and deal_frequencydeals where source ∈ {contract_upload, self_reported} AND status ∈ {accepted, completed}; OR any source with payment_status = settled (money moved through payments); OR any source with a deal_periods row (a contract schedule was extracted from a document).
Explicitly excludedsource = inbox_scan with status set by the summarizer and no settlement; detected / negotiating / pending anything; brand mentions from research (those stay in cultural_relevance / brand_fit, never commercial_proof: signal ownership, §21.1).
Recency windowDeals with term_end or detected_at within 24 months count fully; 24 to 48 months at half weight for renewals_repeat only; older excluded.
Caps (anti-circularity, §14)At most 12 deals counted; verified_commercial_value saturates at the sport × level cohort p90 (the percentile, not raw dollars, is the signal) and until cohorts exist at a fixed alpha ceiling of $50,000 per 12 months; per-deal value capped at $25,000 before summing.
Where the value comes fromdeals.amount (cash + stated product), never commission; the same rule snapshotDealsFor already applies.
What this means for the ten live athletes todayMia keeps the gorjana agreement (self_reported / contract path) and the settled ones; the three source = NULL accepted rows and the inbox_scan accepted row would not count until settled or confirmed. Their scores do not move in Step 0; this policy is read only by the Step 4 engine.

5 · How it rolls out

  1. Dry run per the migration rule: BEGIN; \i migrations/0043_intelligence_foundations.sql; ROLLBACK; against the dev database through the proxy, then checkSchemaDrift.ts with the branch's schema.ts to confirm the only "missing" items are the three the migration creates.
  2. PR to main: CI (typecheck, PGlite suites). Merge → deploy-dev.yml → db-migrate.sh applies 0043 → drift gate green → service replace. Watch it to green.
  3. Verification after deploy: GET /api/v1/athletes/<mia>/score unchanged; the 04:30 refresh runs as before; select count(*) from model_params = 0 (or the drafts if you chose to seed).
  4. Prod receives it on the next promotion through promote.yml; the same script runs there.

6 · Clarifications from the spec itself (small, non-blocking)

  • C1 Two source-class vocabularies (§17 vs §22.3/§28.4). Proposed canonical: the five-value set above, with §17's four mapped onto it.
  • C2 MarketabilityTier is used in §17 and never defined. Left as an open string type until the display policy is decided (your decision 2).
  • C3 MarketabilityResult.potential (0–100) has no definition anywhere in the document. Typed as nullable; nothing will populate it until it is defined.
  • C4 The v3 rate card prices licensing; the §11 taxonomy has no licensing deliverable (closest are the rights add-ons). Kept in the enum so the projection adapter can carry it; needs a home in Step 5.
  • C5 §28.4 sourceClass lists four values while §22.3 lists five (adds inferred). Using five.
