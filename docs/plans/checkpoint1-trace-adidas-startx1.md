# Checkpoint 1 — two governance traces: Adidas (declined) and StartX1 (deferred)

Read-only trace, 27 Sep 2026. Working tree = `fix/checkpoint0-stabilize` (Brain stack tip + audit docs), `main` = origin/main `9fff9b15`; the stack is 70 commits above it. No code changed, no provider called. Dev DB read through a SELECT-only script (deleted afterwards); the Cloud SQL proxy was already running for other `_ckpt_q_*` agents and was left running.

**What Mia experiences today.** She told Nomila two precise things. On Adidas: *"prompt me for my contract and performance data — that's an action, not an objective."* On StartX1: *"evaluate the opportunity first / when u know more about this."* In both cases the app saved her words and then did nothing she can see. No prompt ever reaches her. No research runs. Her words never come back to her.

**What happens underneath.** Both statements are stored as `objective_events.said`. Most of the parts needed to act on them already exist: the contract upload with extraction and a review step, brand research, the Brain's typed `REQUEST_INTELLIGENCE`, a workflow `await_human` step and the reconsideration verdict. What is missing is the wiring between them. Three links break both chains:
1. No durable Intelligence Request store. Brain requests live only in the `brain_runs.output` jsonb or in harness JSON files.
2. Nothing routes a request to an acquisition mechanism for a real athlete, and nothing shows the resulting ask to her.
3. The Athlete State and Brain input never read what the acquisition produces: contract terms and exclusivity, the brand profile.

Legend: **MAIN** = on origin/main. **STACK** = only in the working-tree stack. **dev-deployed** = the table or route exists on dev (flag noted). **EXISTS / PARTIAL / MISSING** is judged relative to the arrow.

## Where Mila would end up doing specialized work herself (risks)
- **Web search in chat.** With `MILA_WEB_SEARCH=true` (off on dev), Mila would answer "what is StartX1?" from ad-hoc Google grounding (`server/mila/loop.ts:184`). That is uncited to any request, unpersisted, and duplicates `researchBrand`. Keep it off for counterparty evaluation; route through `get_brand` → `brandIntel`.
- **`get_brand` triggers research** (`getBrand.ts:4-9`). This is acceptable because it calls the specialized capability, but today it would return the StartX (accelerator) profile as fact, and Mila would relay a probable misidentification.
- **Contract reading.** There is no Mila tool for extraction, which is correct, and the ＋ sheet opens the existing flow. Do not add a chat-side "read my contract" path. Uploaded chat media must not be sent to the extractor from inside the loop.
- **Onboarding-style writes.** `recordAssertions` is the one write exception. Extending the acquisition answer map to free-text "terms" fields would let Mila write commercial facts from chat. Keep commercial terms on the contract path, where the athlete reviews them.
