M.I.A. Score Engine Audit

How an athlete comes into existence, what feeds the marketability score and the rate card, how they are computed, and every process that reads them. Written so the scoring methodology can be replaced with the least possible disturbance downstream.

branch main @ 49b236dengine scoringService v7 · weights v7.2.0rate model v3.1.0-calibrated10 scored athletes in prod
The core finding
The score is well-contained on the way in, loosely coupled on the way out

One pure function computes it, one writer persists it. But 40+ readers consume the stored columns by shape, and most of them fail silently rather than loudly if the shape changes.

The contract to protect
displayScore 200–850 · five tier words · four capitals /100

Those three things are read by the app, Mila, the voice worker, the deal scorer, the Nomi Card and the rate model. Keep them and a new algorithm is a weights-row swap. Change them and it is a cross-cutting migration.

The hidden coupling
Rates are a function of the score

The v3 rate card multiplies market benchmarks by a modifier built from the capitals and the tier word. A new score changes every rate, every deal verdict and every draft counter unless the rate side is re-calibrated with it.

The pipeline in one picture

A · How an athlete comes into the system

There is no "create user" service. An athlete is an athletes row plus an account_roles row, and three doors create or claim one. Auth is Firebase everywhere (Google, Apple, Microsoft code exchange); the server never stores a password.

What the onboarding run does (workflow v2)

The Postgres workflow runner ticks every minute from Cloud Scheduler. The onboarding run is: research (skipped if a research snapshot is under 7 days old) → context_ready (drops the cached generic Nomi Card) → greet (parks until the athlete reacts in chat, voice or form) → doors → wrap. The research step is the first place a score is computed. It also flips status raw → enriched and fills any empty sport, school, conference or division from what research found.

What connecting a platform does

The OAuth callback starts a first_look run per connection: fetch_social (the connect-time fetch, which computes a second score with the platform's real numbers), backfill_recent (30 posts) and compute_first_look (what the posts say, not a scoring input). Gmail and Outlook never score; Spotify keeps an identity-only fetch.

Research and connect are the only two event-driven scorings. After that the athlete is re-scored nightly and re-researched monthly, and nothing else ever touches the score.

C · How the score is computed today (v7.2)

Four capitals, each 0–100, blended by weights that depend on which data exists, then multiplied by a brand-safety factor, then stretched onto a 200–850 display scale with five tier words. The whole engine is server/services/scoringService.ts, pure and synchronous.

internal = round( Σ capital × weight[profile] ) × safety → display = piecewise(internal): 0–80 → 200–710, 80–100 → 710–850

D · How rates are computed, and why they depend on the score

The rate card (rateService.ts, v3.1.0-calibrated) prices each deal type on its own market basis. It reads nothing from the database and none of the scoring weights; its benchmarks are constants in rateModelConfig.ts. It is computed inside writeAthletesCurrent on every score write, so a rate card can never exist without a score.

Narrative is a fifth capital that only rates see. narrativeCapital = min(100, trends×.6 + min(40, gdelt×2)). It is computed in rateService (and, unused, in the engine) and is never stored or shown.

Two silent defaults. A capital missing from the object defaults to 50 inside scoreMod, and a tier word the code does not know simply fails every gate. A new score that renames a capital or a tier will change every rate with no error anywhere.

E · The three writers and the one writer

Three skills compute a score. All three insert an athlete_snapshots row and then call writeAthletesCurrent, which is the only code allowed to touch athletes_current. That discipline is what makes a transition tractable: there is one place where the score becomes columns.

The writer always recomputes the v3 rate card and projects pav and deal_type_rates from it, sets follower columns from the social it scored with, and stamps score_updated_at. Its column list is pinned by athletesCurrentWriter.test.ts.

Two operational facts worth knowing: the 04:30 refresh is an in-process node-cron, not a Cloud Scheduler job, and unlike the inbox sync it takes no advisory lock, so with up to three Cloud Run instances it can run up to three times (the unchanged-skip makes that harmless today). The manual endpoint POST /api/internal/score-refresh-cron?dryRun=true returns per-athlete before/after deltas without writing, which is the readiest tool for a shadow comparison.

H · Things the audit found that the transition must not trip over

  1. silent Rates default missing capitals to 50 and unknown tier words to the lowest gate. A renamed capital or a new tier vocabulary changes every rate with no error. rateService.ts scoreMod, prestigeTier, autographTier
  2. crash reloadWeights throws if the config lacks rateEstimation.brackets (it sorts them unconditionally), even though nothing reads them since the v7 rate model was retired. A clean new weights row without that dead block will fail every scoring at startup. weightsService.ts reloadWeights
  3. silent Mila and the voice worker drop the score card if any of the four capital keys is missing. The client rings render 0 instead. mila/widgets.ts, voice/scoreRoute.ts, mila-voice widgetBridge.ts
  4. history The whole ScoreResult is stored on every snapshot and the voice score-history route reads displayScore / tier from those rows. A new result shape must either keep those two keys or the history reader must be versioned. 272 rows today.
  5. history The engine is path-dependent. Five audience signals need ≥3 prior snapshots; spike and delta terms diff against the previous row. A new algorithm that is not history-dependent will make old and new scores incomparable for the first run and every "unchanged" comparison in refreshScores will fire once.
  6. contradiction Mila's system prompt states "Deals do NOT affect the M.I.A. score", while Commercial capital counts accepted deals and the cold-start profile flips on them (Mia +7 from gorjana). Decide which is true in the new methodology and fix the prompt to match. mila/prompt.ts line 86
  7. baked Deal verdicts bake the athlete's rate into prose stored on the thread. 268 scored threads say things like "cannot compare to her $1,000 per-post floor". A rate change needs a gated re-score (server/scripts/_rescoreImpacted.ts is the existing pattern; it calls Kimi per thread).
  8. cache Nomi Cards are cached and shares are frozen. 9 cached kits across 3 athletes and 2 frozen shares will show the old score until rebuilt (the onboarding run deletes only the generic brand_id 0 kit). Brand-tailored kits are never invalidated by a score change.
  9. deploy Weights swap pattern is one-active-row. The partial unique index means a new version must be inserted inactive and swapped in one transaction (0038 and 0042 are the templates). Dry-run every migration with BEGIN … ROLLBACK against prod and watch the deploy go green; deploy.yml re-creates CHECK lists by hand and they must mirror schema.ts.
  10. stale Three fixtures will drift: __fixtures__/scoringWeights.v7.json (the profile-switch test), the inline weights in server/scripts/testScoring.ts, and the mediaKitService.golden snapshot pinning the "Established" tier text.
  11. hygiene Legacy columns still have fallback readers. pav and deal_type_rates are projections of the v3 card, but the client, chat context, deck rates and voice score still read them as fallbacks. Aditya's row still carries a July card with version "v3", the demo row has none.
  12. hygiene Sport and conference words live in the engine (NATIONAL_KW, CONFERENCE_KW, POWER_CONFERENCES in two files). The no-hardcoding rule says these belong in data. The new methodology is the moment to move them.
  13. ops The 04:30 refresh has no advisory lock and no Cloud Scheduler job; it is an in-process cron on every instance. Fine today because of the unchanged-skip, worth locking before a heavier engine runs nightly.
  14. ops Direct database access from this machine is gone. The public IP changed (38.248.93.149 is not in the authorized networks); the bundled cloud-sql-proxy.exe on port 5440 works.

I · Transition approach with the least downstream risk

The safest shape is the one the codebase already has: a new pure engine beside the old one, selected by the active weights row, shadow-run through the existing dry-run endpoint, then cut over by swapping one row. The decision that sets the size of the job is whether the external contract survives.

1

Fix the contract before the algorithm. Decide, in writing, for each of: display range (200–850?), tier vocabulary (five words?), capital set (four keys, 0–100?), and whether deals feed the score. Keeping all four means the app, Mila, voice, deck and deal pipeline need no change. Any change is a named migration with its own reader list from section F.

2

Add the engine as a second pure function (scoringServiceV8.ts or an engine field on the weights config), returning the same ScoreResult type, with an explicit adapter if the internal shape differs. Keep computeScore's signature so the three writers and refreshScores.unchanged stay untouched. Strip the dead rateEstimation requirement from reloadWeights first.

3

Shadow-run before any write. Insert the new weights row inactive; extend the dry-run script pattern (scripts/_dryRunV72.ts) to compute old and new for all 10 athletes plus the 5 golden athletes, printing score, tier, capitals and the full rate card side by side. Store the grid on the PR the way #363 did. Run evaluateRates.ts against the new capitals so the rate calibration is re-checked in the same pass.

4

Re-calibrate rates deliberately, not by accident. If the capital distribution moves (today audience saturates at 100), the scoreMod blends in rateModelConfig.SCORE_MOD and the tier gates need a matching bump of RATE_MODEL_VERSION. Either pin rates by freezing the old capitals into the rate input during the transition, or version both together.

5

Cut over with one transaction (the 0038/0042 migration shape), then force a full recompute: POST /api/internal/score-refresh-cron writes only on change, so use refreshAthleteScore(id, { force: true }) per athlete or a one-off script. Watch the deploy to green.

6

Re-derive what was baked. Re-score the 268 deal threads (gated, reviewed dry run first), rebuild cached kits for all brand ids, leave frozen shares frozen by design, and refresh the three fixtures. Update the Mila prompt line about deals.

7

Retire the fallbacks in a separate PR. Once every current row carries the new card, drop the readers of pav and deal_type_rates and the momentum block if the new engine does not produce it.

What I need from the new methodology to size the work

  • Output shape: score range, tier names, capital names and scale, anything new the UI should show.
  • Inputs: anything not already on the snapshot (new APIs mean a new writer path and a new snapshot column, not just a new engine).
  • History: whether it needs prior snapshots, and how many.
  • Deals: whether signed deals count, and at what moment.
  • Whether the rate model keeps reading the score, and which capitals it should read.
  • Cadence: nightly is free today; anything heavier needs the lock in H·12.
