What actually recommends
One engine: the inbox deal engine

Classify → score → summarize → rank → voice → draft, ending in a pending action the athlete taps. Every other "recommendation" is either a pitch narrative on a deck, a Mila answer grounded in read tools, or a client heuristic with no data behind it.

Where goals go
Collected in four places, read by one prompt line

Goal slugs are captured at the landing page, confirmed by Mila, proposable from chat and editable on Facts. Downstream, exactly one consumer uses them to decide anything: a "Goals:" line in the deal-scoring prompt.

Weekly plans and schedules
Not built. The spine is an open PR

PR #309 adds a pure occasion finder that reads posted media and live deals. Studio's posting-time and content suggestions are client functions waiting on a fixtures table that does not exist, so they return empty today.

2 · Goals, from capture to every consumer

The vocabulary is one file, shared/goals.ts: five active-athlete slugs, four retired-athlete slugs, and four career statuses. The column is athletes.goal_archetype (text), plus athletes.secondary_goals (jsonb string array) and athletes.brand_voice (jsonb {tone, phrases, avoid}). There is no goals table and no history beyond the assertion ledger.

5 · How each surface is generated

Opportunities · Brief

1

GET /api/v1/me/deals/brief (server/routes/deals.ts:560) calls the shared loader loadRankedDeals: one query joining deals, threads, brands; collapseDealGroups synthesizes one row per deal_group_id (most-advanced status wins, offer borrowed from the richest member, activity summed).

2

composeDealVoice (server/lib/dealVoice.ts) writes Mila's sentence from conversation_state + recommendation_ui + negotiate_terms[0] + economicsState.read, through the A–E fallback ladder, then assertNoUnbackedFigures strips any dollar figure not backed by a structured field.

3

dealRanking orders by awaiting-athlete, then deadline proximity, then scoreNumeric, then freshness. The route keeps detected/pending/negotiating, returns the top 3 and counts.

4

Client BriefView → AskCard → DecisionSheet (position, why, plan from negotiate_terms) → NegotiateComposer (three-number strip from rate card + floor, draft_points chips) → pending_actions proposal → approve sends through threadReply. Ask-for-terms batch and Your Week are pushed screens off the same tab.

Opportunities · Your Week, Filtered, Explore

Your Week is a 30-day receipt built on the client from agent_actions (set-aside list, track record, Undo/Wrong) and deals (arrived / you moved / still waiting buckets in weekLogic.ts and yourWeekOutcomeLogic.ts). Filtered lists agent_actions rows with payload.kind = junk grouped by noise_reason. Explore All renders ClassicListV2 over the same ranked loader with archived threads hidden.

Mila chat

POST /api/v1/me/chat → runMilaLoop. The prompt (server/mila/prompt.ts) carries persona and rules only: lead with a take, one list_deals call for ranking questions, at most two deep dives, never a count, widget directive on the last line, draft never sends. Tools: get_score, get_profile, list_deals, get_deal, get_rate_card, list_tasks_threads, get_analytics, draft_reply, navigate, get_help, get_brand, get_brand_fit, plus get_first_look and complete_onboarding_step in onboarding. After the answer: a rolling conversation summary, a suggestions call, and profile-candidate extraction. Chat openers per screen are a static list in client/screens/milaOpeners.ts. The v1 inline prompt path (chat.ts:300–420, Kimi, score and last 10 deals stuffed into the system prompt) is still in the file behind the flag.

Mila voice

Separate repo (nomila-co/mila-voice, LiveKit). Tools: get_score, open_draft, list_deals, get_athlete_profile, get_deal_brief (brand or campaign name, resolves deal → brand → fit in one call), get_thread, get_score_history, get_share_signals, web_search when MILA_VOICE_WEB_SEARCH, complete_onboarding_step in onboarding. Every read goes through /api/internal/voice/* routes that return closed enums and ids, never brand prose. Memory is voice_context (ids and enums only) rendered to one seed sentence by voiceSeed.ts; the text loop also writes it.

Brand tab

Score screen and rings read /athletes/:id/score. Deck and Rates read the kit and the rate card. Facts reads GET /me/record (said / found / made with provenance). Story shows only story_arc from the record's numbers group; the tab's own comment says narrative, stories, voice and direction are not built. Growth is the analytics read API (deltas only, no advice).

Pitches and brand recommendations

A pitch is a media_kits row with brand_id > 0; status is derived (ready / sent / opened / stale) from card_shares and card_share_views (server/services/pitches.ts). Pitch insights recompute whyFits angles per request with an empty facts array and are not stored. The only brand ranking in the codebase is GET /athletes/:id/brands (server/index.ts:1183): brands from the athlete's own inbox threads, sorted by a hard-coded deal-warmth map (negotiating 100 … rejected 0) then recency. There is no brand discovery beyond what has already emailed her, and no brand-to-athlete matching.

Studio

Now feed = what is rendering (made shelf) + owed deliverables (listOutstandingDeliverables, 0 rows today) + fixture suggestions (personalLogic.suggestionsFrom, which needs fixtures; useFixtures returns a stub empty array, so no suggestion ever renders). Make it = assembleBrief with an objective the athlete picks (announce, showcase-product, grow-following, concept, recap, thank-partner) and a deliverable (post, story, reel, carousel, ad, clip). Posting time = scheduleLogic.recommendedSlot, three hours before the next fixture, also fixture-dependent. Personal post concepts = a regex table (CONCEPTS) matching the athlete's typed purpose. Nothing schedules or publishes; every OAuth scope is read-only.

Nomi Card

assembleMediaKit: getAthleteContext → deriveDeckPlan (rules: brand mode adds whyFits, campaignConcept, activationPlan; achievements card when ≥3 achievements and ≥1 national) → shot list → in parallel: Curator, Narrator, whyFits, concept, activation plan → cards → cached in media_kits, invalidated only for the generic kit by onboarding. Rates card packages are computed from the headline post rate (series = 3 posts × 0.94). The "activation plan" is the closest thing to a content calendar in the product and it is a per-brand pitch card, not a plan for the athlete.

9 · Duplicated logic

  • Brand fit written three ways. Kit build stores whyFits inside media_kits.data; the voice path stores the same three angles in brand_fit_narratives; pitchInsights and get_brand_fit recompute per call and store nothing. mediaKitService.ts · voice/brandFitFill.ts · services/pitches.ts · mila/tools/getBrandFit.ts
  • Five readers of the athlete's current row assemble their own context. getAthleteContext, buildNarratorContext, deriveShotList's fallback query, chat.ts v1 inline prompt, and loadOnboardingFacts each select from athletes + athletes_current + latest research snapshot.
  • Brand tier and category exist twice. The scorer takes brandTier and category from Kimi's brandAnalysis of the email; inbox_brands carries a researched brand_tier and category that the scorer never reads.
  • Three ranking systems. Server dealRanking for the Brief, the client's score-sort in use-deals.ts (noted in dealRanking's header), and the brands list warmth map.
  • Three memories. Thread conversation_state (Kimi), Mila conversations.summary (model), voice_context (ids). Deal history for voice is rebuilt from structure by design.
  • Two chat implementations in chat.ts: the v1 inline Kimi prompt and the v2 loop, switched by MILA_AGENT_V2.
  • Rate reads. deriveDealTypeRates in dealDetector, dealDraft, dealValueStore; resolveAthleteRate in dealVoice and offerMoney; deckRateFigures in the kit.
  • Sender knowledge was in three places (preFilterEmail, senderMemory, emailFilters) and is being consolidated into senderProfile; the header documents 25 of 46 muted senders never reached memory.
  • Capital grade thresholds differ between the kit (80/60/30) and the client rings (80/60/40/20).
  • Deliverable parsing exists in mila/deliverables.ts (voice) and in askTerms' missing-terms detection from offer_struct, on different fields.
