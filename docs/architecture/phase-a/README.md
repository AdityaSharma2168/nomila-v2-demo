## Incidents

### 11 Sep 2026 — production migration dry-run committed (Step 2d-6 preparation)

**Cause.** A hand-chained migration "dry-run" (`0031 … 0050` concatenated) was wrapped in an outer `BEGIN … ROLLBACK` and run against the production database. Migrations `0040_weights_v7_1_no_story_arc_bonus.sql` and `0042_weights_v7_2_no_major_schools.sql` contain their own `BEGIN;`/`COMMIT;`. The inner `COMMIT` terminated the outer transaction, so every statement after it autocommitted; the final `ROLLBACK` had nothing left to roll back.

**Verified blast radius (read-only inspection afterwards).** `0031–0043` were already present on production and re-ran idempotently (the `scoring_weights` rows v7.1.0 / v7.2.0 carry their original 7 Sep timestamps, once each; v7.2.0 stays active). `0044–0050` **schema objects were created**: the Step 1a social substrate tables, the Stories trigger, the research substrate, the planner tables, `athlete_index_v` + `athlete_index_matches`, `athletes_auth_id_uq`, `athlete_affiliations.fact_id` + its index. **Zero application data rows changed** (production holds 0 athletes / affiliations / facts / research runs / workflow runs / inbox threads; the `UPDATE`s in 0031 and 0036 touched nothing). The production Cloud Run revision (`nomila-v2-prod-00001-zcv`) and its flags are unchanged; no production code reads the new objects.

**Decision (user).** Option 1: leave the production schema exactly as it is; no revert, no drop, no reconciliation command against production. Recorded here; production is not touched again in that session.

**Bookkeeping state — schema present ≠ migration recorded as applied.** Read-only diagnosis of the migration machinery:
- `scripts/db-migrate.sh` is the only schema path. Step 2 (`drizzle-kit migrate`) is the ONLY step with a ledger: `public.__drizzle_migrations` records the journal migrations `0000–0011` by hash + timestamp (production: 13 rows, last 22 Jul 2026 — identical to dev). Step 3 re-runs the hand-written files `0031–0050` on EVERY deploy in fixed order with `psql -v ON_ERROR_STOP=1`; there is **no ledger, no checksum and no version record** for them — their only "state" is the physical schema, and each file is written to be idempotent (`IF NOT EXISTS` / `NOT EXISTS`-guarded / `DROP … ADD`).
- Therefore `0044–0050` are **schema-present on production but not, and never, "recorded as applied"** — nothing in the system records hand-file application, on any environment.
- Step 5 (`checkSchemaDrift.ts`) compares `shared/schema.ts` `pgTable` columns against `information_schema.columns` only — physical schema, never migration history; it fails only on a code column missing from the database.
- What the next normal production deploy will do for each of `0044–0050`: re-run the file; every statement is `IF NOT EXISTS`-guarded (see the per-file review in the 2d-6 PR), so each reports "already exists, skipping" and changes nothing; the drift gate then compares `schema.ts` to the physical schema and passes because the objects exist. No ledger entry is written for them, exactly as on dev. That is the reconciliation path: nothing to reconcile manually, because the machinery never recorded hand files anywhere.

**Permanent process rule (adopted).** Production migration validation is never a chain of files inside an outer transaction. Before any production migration validation: inspect each file for `BEGIN` / `COMMIT` / `ROLLBACK` / `START TRANSACTION`, `DO` blocks, and non-transactional DDL (`CONCURRENTLY`, `VACUUM`, `ALTER TYPE … ADD VALUE`); validate files individually; use the runner's own mechanism where one exists; never assume an outer rollback protects against files with transaction control; a production command requires explicit approval naming the exact command. Static guard: `server/migrationsGuard.test.ts` (CI) fails on any migration file with transaction control that is not on its explicit allow-list (today: 0040, 0042) and on non-transactional DDL.
