Where the code already agrees
Storage discipline, versioned weights, tap-to-act, source precedence

Append-only snapshots, a one-active-row weights table, the athlete-asserted ledger with provenance, a connected > discovery > research resolver, and pure engines that never query the database are all in place. These are KEEP.

Where it diverges most
The signal layer does not exist

Today raw platform aggregates go straight into four capitals through hand-set point tables. Beta.1's core is a Signal Engine with cohort percentiles, priors, confidence and provenance between evidence and score. That layer is ADD, and it is what the doc names the immediate milestone.

What to raise before touching anything
Six conflicts with LOCKED or frozen decisions

Research provider, the 0 vs 200 floor of the 850 scale, eight dimensions against four locked ring colours, tier vocabulary, commercial-proof circularity, and research "never forgets" versus as-of dates. Section 9.

10 · Execution sequence, for discussion

You asked to work module by module in the order Identity → Research → Profile → Social → Marketability → Rates → Commercial. The spec's own definition of done (§25, §30, §31) puts the Social Intelligence data layer first. Both orders end in the same place; the difference is what ships first without touching production behaviour. My recommendation is below, with the reason. Nothing starts until you pick.

0

Foundations, no behaviour change. Versioned parameter store (extend scoring_weights or a new table), asOfDate on snapshots, the NormalizedSignal / SocialMetricObservation / RateEstimate types, and pulling origin/main so migrations use the new schema flow. Small PR.

1

Social Intelligence data layer (section 5). Observation and feature tables, adapters extracted from the existing fetch code, secret sanitization, the feature calculator, Mia fixtures, and the one command that produces her feature vector for an asOfDate. Additive: the daily snapshot and the current score keep running. This is the spec's immediate milestone and the input every later engine needs.

2

Research provider and canonical profile (sections 3 and 4). ResearchProvider interface, OpenAI adapter run in shadow beside Gemini for the ten live athletes, the AthleteResearchProfile schema with evidence and provenance, cost telemetry, TTL-based refresh. Decision 1 and 5 first.

3

Identity confirmation (section 2). Onboarding v3 with identify + confirm before research. Decision 6 first. Small once the provider exists.

4

Marketability Beta.1 in shadow (section 6). Signal Engine, cohort tables, priors, confidence, drivers, the 37-athlete + holdout harness, shadow scores for the live athletes, then cutover by weights-row swap with the projection adapter from the score audit. Decisions 2, 3, 4 first.

5
